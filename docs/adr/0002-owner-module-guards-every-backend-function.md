# ADR-0002 — 소유자 확인을 백엔드 함수 전체의 통과 지점으로 만든다

- **상태**: 수용됨 — 구현 대기 (결정만 확정, 코드는 아직 바꾸지 않음)
- **날짜**: 2026-08-14
- **관련**: `CONTEXT.md`(소유자) · `convex/auth.ts`의 Option A/B 결정 게이트 · ADR-0001

## 맥락

백엔드 공개 함수 20개가 호출자가 건네준 사용자 id를 그대로 믿고, 문서 id만 받아 수정·삭제한다.
실제로 신원을 확인하는 코드는 `auth.ts` 두 곳뿐이고, "신원에서 유도하고 소유권을 확인하라"는 규칙은
네 파일에 복붙된 주석으로만 존재한다. 규칙이 코드가 아니라 산문으로 있는 상태다.

호출부가 아직 0이라 지금이 가장 싸게 고칠 수 있는 시점이다.

## 결정

**소유자를 해석하고 소유권을 확인하는 module 하나를 두고, 모든 백엔드 함수가 그 앞을 지나가게 한다.**

- 신원 확인은 **구조로 강제한다.** 함수 선언을 감싸는 래퍼를 직접 만들어(새 의존성 없이),
  본문이 시작되는 시점에 소유자가 이미 해석돼 있게 한다. 래퍼를 쓰지 않은 함수는 눈에 띄고
  리뷰에서 기계적으로 감사된다.
- 소유자를 해석할 수 없으면(미인증이거나 첫 로그인이라 레코드가 없으면) **항상 거부한다.**
  화면이 로그인 전까지 구독을 걸지 않는 방식으로 게이트하고, 사용자 레코드 생성은
  로그인 직후의 별도 함수가 책임진다. (읽기 함수는 쓰기가 불가능하므로 그 안에서 자동 생성할 수 없다.)
- 소유권 확인은 **문서를 가져오면서 소유자까지 검증하는 함수 하나**로 한다. 수정하려면 어차피
  문서를 가져와야 하므로 자연스러운 경로가 곧 안전한 경로가 된다.
- 확인 대상은 수정할 문서만이 아니라 **인자로 들어온 참조 문서까지**다. 폴더 이동의 대상 폴더,
  노트의 소속 폴더, 태스크가 가리키는 노트, 첨부가 붙는 노트 — 남의 것을 가리키는 것도 막는다.
- 사용자 id 인자는 20개 함수 interface에서 **사라진다.**

## 고려한 대안

- **규약(각 함수 첫 줄에서 확인 함수를 호출)** — 지금 주석에 있던 규칙이 "불러야 하는 함수"로
  바뀔 뿐이다. 잊으면 아무도 못 잡는다는 실패 방식이 그대로 남는다.
- **데이터 접근 자체를 소유자 범위로 감싸기** — 잊을 수 없다는 점은 가장 좋지만, 백엔드가 제공하는
  데이터 접근 표면(쿼리 빌더·인덱스·수정·삽입·삭제)을 통째로 재현해야 한다. module은 작은
  interface 뒤에 복잡도를 숨겨야 하는데 그 반대가 된다. 부분만 감싸면 사람들이 원래 경로로
  빠져나가므로 더 나쁘다.
- **인자 이름 규약으로 자동 검사** — 규약을 벗어난 인자에서 조용히 뚫린다.
- **해석을 또 하나의 교체 가능한 자리로 분리** — 지금 구현이 하나뿐이라 가설적인 자리다.
  실제로 둘이 되기 전에는 두지 않는다.

## 결과

- `auth.ts`의 Option A/B 결정 게이트는 **지켜진다.** 신원 해석을 이 module 안에 넣으므로,
  나중에 다른 방식으로 바꾸더라도 함수 20곳이 아니라 이 module 하나가 바뀐다.
  게이트를 어기는 것이 아니라 게이트를 싸게 만드는 방향이다.
- **예외는 `auth.ts`의 두 함수뿐이다.** 사용자 레코드를 만드는 함수는 래퍼보다 앞서야 하고,
  현재 사용자를 묻는 함수는 로그아웃일 때 "없음"을 돌려줘야 화면 게이트가 성립한다.
  규칙은 예외에서 무너지므로 이 둘은 코드에 명시적으로 남긴다.
- 검증은 래퍼 자체(미인증·레코드 없음·정상)와, 문서를 id로 건드리는 함수마다
  "남의 문서는 거부된다" 케이스 하나씩으로 한다. 소유권 확인을 빠뜨린 함수를 잡는 것은 후자뿐이다.
- 전환은 20개를 한 번에 한다. 두 관습이 공존하는 구간을 만들지 않는다.

## 이 결정을 뒤집어야 할 신호

- 노트 공유(읽기 전용 링크, REQUIREMENTS 미결 1번)가 도입되는 경우. 소유자가 아닌 사람이
  노트를 읽는 첫 사례이므로 "소유자만 읽는다"는 전제가 깨진다. 그때는 공유를 별도 개념으로
  세울지, 소유자 정의를 넓힐지 결정해야 한다.
- 팀·워크스페이스(REQUIREMENTS 미결 5번)가 생기는 경우. 문서의 소유자가 한 명이라는
  전제 자체가 바뀐다.
