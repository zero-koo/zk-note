# ADR-0003 — 노트의 원본은 마크다운 문자열이다

- **상태**: 수용됨
- **날짜**: 2026-08-14
- **관련**: `docs/ARCHITECTURE.md` §10.1(갈림길) · §9.3(LWW) · §3(스키마) · `docs/REQUIREMENTS.md` §10-9

## 맥락

노트 본문을 어디에 두느냐가 MVP 의 마지막 선결 과제였다. 두 갈래가 있었다.

- **A. 마크다운 = 원본** — `notes.content` 에 표준 마크다운 문자열. 현 설계.
- **B. `prosemirror-sync` = 원본** — 본문이 컴포넌트가 관리하는 스냅샷+steps 가 되고,
  마크다운은 Export 시 파생된다.

스키마·검색 인덱스·Export·오프라인 버퍼가 모두 이 선택에 종속돼 있었다(§10.1).

A 의 전제는 "커스텀 노드를 품은 마크다운이 에디터를 왕복해도 그대로 남는다"였고, 이건
검증되지 않은 가정이었다. 깨지면 A 는 성립하지 않는다.

## 결정

**A 를 택한다. 노트 본문은 `notes.content` 의 표준 마크다운 문자열이 원본이다.**

## 근거 1 — 왕복은 성립한다 (실측)

버려질 프로토타입으로 마크다운 → TipTap → 마크다운 왕복을 16개 케이스에 대해 측정했다.
종이 위에서 판단이 서지 않는 것들만 골랐다.

| 판정 | 뜻 | 건수 |
|---|---|---|
| 보존 | 입력·출력이 바이트까지 동일 | 14 |
| 서식변형 | 출력을 다시 파싱하면 같은 문서 — 내용은 온전, 파일만 재포맷 | 2 |
| **손실** | 다시 파싱하면 문서가 달라짐 | **0** |

판정을 바이트 비교 하나로 두지 않고 **"출력을 다시 파싱해 같은 문서인가"** 축을 더한 것이
핵심이었다. 바이트만 봤다면 재포맷을 손실로 오해했을 것이다.

특히 확인된 것:

- `- [ ] 제목 <!-- task:abc123 -->` — §10 이 약속한 태스크 id 주석이 살아 돌아온다.
  노트 체크박스와 태스크를 잇는 장치라 이게 안 되면 §6.4 가 무너진다.
- `[[노트이름]]` — 한글, 공백 포함 제목, 한 줄에 여러 개 모두 통과.
- **오탐 없음** — 코드블록 안의 `<!-- task:notreal -->` 은 태스크로 잡히지 않고,
  `arr[[0]]` 은 위키링크로 잡히지 않는다. 데이터 오염 경로가 막혀 있다.
- 중첩 리스트 안의 태스크도 들여쓰기와 id 가 함께 유지된다.

> **참조 구현**: 프로토타입은 폐기됐다. 커밋 `55bb32a` 의
> `src/lib/editor/prototype-source-of-truth/roundtrip.ts` 에 확장 정의(WikiLink·TaskNode —
> 위 함정 1~3의 동작하는 해법)와 시험 케이스 16개가 남아 있다 (`git show` 로 회수).
> 측정 환경은 `@tiptap/* 3.30.0` + `tiptap-markdown 0.9.0`. 직렬화의 `state.out` 후처리는
> 프로토타입 품질이므로 실코드로 옮길 때 재설계할 것(함정 4).

## 근거 2 — B 의 대가가 우리 로드맵과 충돌한다

B 는 동시편집 유실을 없애지만 §10.1 이 적어둔 제약에 **오프라인 편집 미지원**이 있다.
`REQUIREMENTS` Phase 2 에는 오프라인 지원이 들어 있다. 즉 이 선택은 "안전 vs 단순"이 아니라
**동시편집이냐 오프라인이냐**의 교환이었다.

개인용 노트 앱에서 "동시편집"은 협업이 아니라 **내 기기 두 대**를 뜻한다. 같은 노트를 두 곳에
동시에 열어두고 양쪽에서 고치는 상황은 드물다고 판단했다. 반면 오프라인은 노트 앱에서
일상적으로 아쉬운 기능이다. 그래서 오프라인 쪽을 열어두는 A 를 택한다.

## 받아들이는 대가

- **동시편집 유실 위험은 남는다.** 같은 노트를 두 기기에서 동시에 편집하면 나중에 저장한 쪽이
  상대의 편집을 **통째로** 덮어쓴다(§9.3 LWW). 한 글자가 아니라 그 세션 전체다.
  완화는 하되(저장 전 갱신 감지, 충돌 시 사용자에게 알림) 근본 해결은 아니다.
- **저장할 때마다 파일이 재포맷된다.** 측정된 두 건: 태스크 목록 항목 사이에 빈 줄이 생기고
  (loose list), `*` 가 `\*` 로 이스케이프된다. 렌더 결과는 같지만 사용자가 친 것과 파일이
  달라진다. 버그가 아니라 성질로 받아들인다.

## 구현할 때 반드시 지켜야 할 것 (프로토타입이 비싸게 알아낸 것들)

1. **StarterKit v3 에는 Image 도 Table 도 없다.** 따로 등록하지 않으면 이미지와 표가 통째로
   사라진다 — 조용한 데이터 손실이라 제일 위험하다. `@tiptap/extension-image`,
   `@tiptap/extension-table` 이 필요하다.
2. **tiptap-markdown 은 markdown-it 으로 HTML 을 만든 뒤 TipTap 의 HTML 파서에 넘긴다.**
   따라서 커스텀 인라인 문법(`[[...]]`)은 markdown-it 규칙만으로 부족하고 **렌더러까지** 붙여
   HTML 을 내보내야 한다. 규칙만 넣었을 때 위키링크가 통째로 증발했다.
3. **태스크 id 주석 파싱은 `parse.updateDOM` 에서 HTML 주석을 data 속성으로 옮긴다.**
   중첩 리스트가 있으면 바깥 `li` 가 안쪽 주석을 삼키므로 **자기 소유의 체크박스·주석만**
   봐야 한다. 이걸 안 하면 부모 항목에 자식의 id 가 붙는다.
4. 직렬화 쪽은 프로토타입에서 `state.out` 후처리로 때웠다. 실코드로 옮길 때 다시 설계할 것.

## 이 결정을 뒤집어야 할 신호

- 동시편집 유실이 실제로 발생해 사용자가 내용을 잃는 경우. 한 번이라도 겪으면 B 재검토가
  정당하다. 그때 옮겨야 할 것은 스키마·검색 인덱스·Export·오프라인 버퍼 전부다(§10.1).
- 팀·협업 기능(REQUIREMENTS 미결 5번)이 로드맵에 들어오는 경우. "동시편집은 드물다"는
  이 결정의 전제가 그 순간 무너진다.
- Convex 공식 sync 엔진(`curvilinear`)이 alpha 를 졸업해 오프라인과 병합을 동시에 주는 경우.
  그러면 교환 자체가 사라지므로 다시 볼 값어치가 있다.
